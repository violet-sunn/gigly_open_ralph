# e2e-journeys-and-greenup

## Why

Reconciliation change #16 — the **final** change of the E2E reconciliation plan (`openspec/planning/e2e-reconciliation.md`). The two cross-screen **journey** specs and the **error-scenarios** spec chain the per-screen flows end-to-end, so they were deferred until the single-screen deltas (changes #3–#14) were known. They still drive the **old kit** DOM (English action labels, the pre-reground accept-on-gig-detail flow, a `textarea[name="workDescription"]` submit form) and `error-scenarios.spec.ts` additionally references **two Gig fields that do not exist** (`workSubmittedAt`, `completedAt`) — the pre-existing tsc errors the plan flagged. This change reconciles all three to the rebuilt screens over the **unchanged** gig-lifecycle data layer/actions, then runs the **whole** suite to confirm every spec (rewritten + every PASS-AS-IS spec) is green — closing out the initiative.

Investigated facts:

- **The Gig lifecycle is `status` + `paidAt` only.** `prisma/schema.prisma` `model Gig` has `status` (`OPEN`→`IN_PROGRESS`→`REVIEW`→`COMPLETED`→`PAID`) and `paidAt`; there is **no** `workSubmittedAt` or `completedAt` column. `error-scenarios.spec.ts` reads `gigAfter?.workSubmittedAt`/`completedAt` (lines 338, 391) and seeds `createTestGig({ …, workSubmittedAt/completedAt: new Date() })` (lines 357, 507, 559). Those refs are the tsc errors and must be dropped — `status: 'REVIEW'`/`'COMPLETED'`/`'PAID'` already encodes the same state the assertions check (the surrounding `status` assertions remain).
- **`client-journey.spec.ts`** drives the full lifecycle via UI with stale labels/flow: it creates the gig with the **old flat form** (`textarea[name="acceptanceCriteria"]`, `input[name="tags"]` filled directly) and expects a dashboard redirect; it **accepts on the gig-detail page** (`button:has-text("Accept")`); it approves (`button:has-text("Approve")`) and marks paid (`button:has-text("Mark as Paid")`) on gig-detail. In the rebuild: create-gig is `CreateGigDesign` (criteria editor populates the hidden `input[name="acceptanceCriteria"]`, category chip sets `input[name="category"]`, tag chips set `input[name="tags"]`; submit «Опубликовать гиг» → redirect `**/gigs/new/success`); **accept moved to `/gigs/[id]/applications`** (`ApplicationsDesign` «Принять»); approve is «Принять работу» and mark-paid is «Отметить как оплаченный» on the rebuilt `GigDetail`. The programmatic specialist steps (apply seed, submit-work via `status:'REVIEW'`) stay.
- **`specialist-journey.spec.ts`** is mostly programmatic; its UI steps are browse (`/gigs` → click the gig card) and apply. The apply form selectors are stable **except** `textarea[name="estimatedEffort"]` — the rebuilt `GigDetail` apply form uses `input[name="estimatedEffort"]` — and the submit should target the «Отправить заявку» button rather than a bare `button[type="submit"]`.
- **`error-scenarios.spec.ts`** ACL/redirect tests are largely DOM-agnostic and should hold, but the few label assertions are stale: `button:has-text("Submit Application")` → «Отправить заявку», `button:has-text("Approve")` → «Принять работу», `button:has-text("Mark as Paid")` → «Отметить как оплаченный», and the `textarea[name="workDescription"]` submit-work form → the rebuilt «Сдать работу на проверку» button (assert it is absent for a non-assigned specialist).
- **Full-suite greenup.** After the rewrites, `npm run clean:test-db && npm run test:e2e` MUST report **0 failures** across all 40 specs — including the PASS-AS-IS specs (`auth-*`, `csrf-protection`, `gig-browse-access`, `admin-moderation`, `admin-pagination`, `theme-coverage`, `register-*`, `registration`, `*-onboarding`, `login-role-param`, `fidelity`). Any straggler is fixed **tests-only** (or a genuine app issue is flagged to the user before any minimal fix).

This change is **tests-only** (no `app/`/`lib/` behaviour change) — the gig-lifecycle actions (`createGig`, `acceptApplication`/`rejectApplication`, submit/approve/mark-paid, `openDispute`) and the Gig schema are unchanged; the specs are repointed at the rebuilt screens and the real schema fields.

## What Changes

- **REWRITE `__tests__/e2e/client-journey.spec.ts`** to chain the rebuilt screens: create-gig via `CreateGigDesign` (replicating the green `compose-create-gig` fill: title → category chip → description → goal → deliverables → criteria editor «Добавить» → budget → deadlineDays → «Опубликовать гиг» → `**/gigs/new/success`), accept on `/gigs/[id]/applications` via «Принять», approve via «Принять работу», mark-paid via «Отметить как оплаченный»; keep the programmatic apply seed + `status:'REVIEW'` submit-work step and the final DB state assertions (status `PAID`, `paidAt` truthy, ACCEPTED application, budget math).
- **REWRITE `__tests__/e2e/specialist-journey.spec.ts`** apply step: `input[name="estimatedEffort"]` (not `textarea`), submit via the «Отправить заявку» button; verify the browse → gig-card → detail navigation against the rebuilt screens; keep the programmatic client/accept/submit/approve steps and final assertions.
- **REWRITE `__tests__/e2e/error-scenarios.spec.ts`**: drop the non-existent `workSubmittedAt`/`completedAt` reads and seeds (the `status` assertions already encode the state); update the stale labels («Отправить заявку», «Принять работу», «Отметить как оплаченный») and the submit-work-form absence check (the «Сдать работу на проверку» button is absent for non-assigned specialists); keep the unauthenticated-redirect and RBAC scenarios (verify they still pass against the rebuilt routes).
- **GREENUP:** run `npm run clean:test-db && npm run test:e2e`; fix any remaining red **tests-only** until 0 failures; confirm every PASS-AS-IS spec still passes.
- Reuse the harness (`setE2ESession`/`createTestSession` one-arg + cookie, direct Prisma seeding into `file:./test.db`, `DISABLE_RATE_LIMIT=true`).

## Impact

- **Affected:** `__tests__/e2e/{client-journey,specialist-journey,error-scenarios}.spec.ts` (rewritten); a shared **FK-safe `resetE2EDb()`** helper added to `__tests__/helpers/seed.ts`; the unscoped `deleteMany()` cleanup replaced in `auth-session`, `csrf-protection`, `gig-browse-access`, `gig-pagination`, `messaging-flow-e2e` + the two journeys + `error-scenarios`, and a reset-before-seed added to `compose-gig-search`. All tests-only.
- **Not touched:** `app/`/`lib/` behaviour (the gig-lifecycle actions, `CreateGigDesign`/`GigDetail`/`ApplicationsDesign`, the Gig schema); the unit/integration suite (951/951).
- **Greenup outcome (revised by user decision "fix isolation, flag auth-flow"):** the first whole-suite run exposed **47 failures**, dominated by FK-unsafe cleanup; the tests-only isolation fix brought it to **13 failures / 186 passed**. The residual 13 **all fail in isolation on a clean db** — pre-existing content drift in PASS-AS-IS specs (auth/register-wizard ×9, `csrf-protection` stale create-gig fill ×1, `gig-browse-access` old-kit UI ×3), neither caused by this change nor pollution. They are **flagged** in `openspec/planning/e2e-greenup-residual.md` for a dedicated follow-up (`e2e-greenup-residual`) rather than expanded here.
- **Plan:** advances `openspec/planning/e2e-reconciliation.md` from 15/16 → **16/16** (journey/error rewrites + suite-wide isolation fix complete; the full suite is green **except** the flagged pre-existing PASS-AS-IS content drift).
