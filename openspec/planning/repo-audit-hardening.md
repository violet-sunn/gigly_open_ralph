# Repo Audit Hardening — Security, Data Integrity, Scale, Lean

**Created:** 2026-10-20
**Status:** PLANNED

## Problem

A whole-repo quality audit (2026-10-20, `/ponytail-audit`: read the deploy/build config, schema, every server action, the session/rate-limit/notification/SSE libs, the view-model layer, and the test layout) found **18 defects** that the three stress-test rounds did not cover because they are not visible from the UI. Each was **verified by reading the code path end to end**, not by a report. They break down as:

- **Security promises that are not kept** — a login token is never re-checked against the database, so an admin «Заблокировать» and the Settings «Завершить сеансы» buttons do nothing to an open tab for up to 7 days; anyone can set their own «verified» badge through a hidden form field; the login rate limiter keys on a spoofable proxy header and also counts successful logins; a production client account ships with the public password `TestPass123`.
- **Data-integrity holes** — the self-service «Удалить аккаунт» purges other users' PAID gigs, reviews and chats and strands IN_PROGRESS gigs with no specialist (the admin delete has guards; the self-delete has none); the container applies schema changes with `--accept-data-loss` on every boot; email is matched case-sensitively and never trimmed, so a mobile signup can lock itself out with no password reset.
- **Code that will not hold as data grows** — every protected page render, SSE push and poll loads *every* chat message the user ever exchanged (twice) just to count unread ones; one rating query per card; submit buttons are not disabled while pending and the accept path has no row guard, so double-clicks crash or double-assign.
- **Bloat and duplication** — about 6,500 deletable lines: 4,821 lines of archived «legacy test» scripts, ~1,550 lines of components nothing renders, dead `lib` helpers (one computing a **10% fee** next to the 17.5% SSOT), a 221 KB SQLite backup tracked in git, two unused dependencies, the same specialist/client gig board computed twice with different rules.

## Why This Matters

The product is positioned as a «high-end B2B marketplace» («Russian Toptal Lite», *Trust Through Transparency*, per `project.md`). A platform whose block and session-termination controls are decorative, whose trust badge is self-assignable, and whose demo client can be logged into by anyone who reads the repo is not trustworthy, whatever the UI says. The self-delete hole can erase a specialist's whole earnings history (`Финансы` → «Заработано» drops to zero) with one click by someone else — exactly the «payment delays / quality disputes» trust deficit the product claims to solve. The unbounded message scans are the one query whose cost rises with every message ever sent, on the hottest path, in a single SQLite process. And the dead 10%-fee helper is a loaded gun for the next contributor. Every Must-fix item is under 30 lines; closing them as one coordinated round — security/integrity first, then scale, then lean — keeps the fixes reviewable and revertable instead of a scatter of patches.

**Risks / unknowns:**
- **A1 cost.** `getSession` runs several times per request (layout + page + actions). Adding one primary-key `Session` lookup per call is sub-millisecond in SQLite but is a new DB hit on every request. Acceptable; if it ever shows up, cache per request with React `cache()` — do not skip the check.
- **A1 backward compat.** Tokens issued before the `Session` row existed carry no `sid`; the vitest harness mints `sid`-less JWTs (`session-tracking.test.ts:75` asserts they validate). Keep tolerance for `sid`-less tokens (check `user.suspended` by `userId` only), require the row when `sid` **is** present. Do not break the harness.
- **A3 data migration.** Lower-casing existing `User.email` rows can collide if two accounts already differ only by case. The change MUST query for case-only duplicates first and stop (report them) rather than fail mid-update.
- **B1 proxy behaviour is unconfirmed.** Whether Amvera's proxy *appends* or *replaces* `X-Forwarded-For` was not verifiable from the repo. Taking the **last** entry is correct in both cases (the trusted proxy always appends/sets it last); taking the first is correct in neither. Verify once post-deploy by logging the raw header for one request.
- **B3 behaviour change on deploy.** Without `--accept-data-loss`, a destructive schema change makes the container exit at boot (`set -e`) and the **old** container keeps serving. That is the intended trade (outage over silent loss), but the deployer must know a failed boot now means «decide by hand», not «retry».
- **C1 correctness.** The unread rule is subtle: messages from *others* (`senderId != viewer`, system `senderId = null` excluded on the chats side but **counted** on the bell side today — see `notifications-read.ts` L34 vs `view-models.ts` L1109). The rewrite MUST keep one explicit rule and the existing tests (`live-counts`, `notifications`, `chats-vm`, `recent-messages-vm`) green; do not «fix» the system-message discrepancy silently — pick one rule and state it in the spec.
- **C3 product decision.** The dashboard and `/my-gigs` disagree on whether archived applications (rejected/withdrawn) are shown. Default recommendation: **show them under «Все» on both** (nothing is lost; matches the `withdrawn-status-truthfulness` intent). Confirm with the user before implementing.
- **D2 kit decision.** The wider blocks/primitives kit (~4,000 lines) is alive only through `/workbench` (dev-only, 404 in prod) and four named imports (`Icon`, `Button`, `SectionHeader`, `Notice`). D2 deletes only the files with **no importer at all**; whether to keep the workbench catalog or fold those four pieces into `app/_design` and drop the kit is a separate decision — **do not** expand D2 into it.

## Non-goals / Deferred

- No design re-grounding, no new UI kit, no responsive work.
- No change to the gig lifecycle / application state machine beyond the OPEN-guard in `acceptApplication` (B4).
- No real payment gateway, no real phone/INN verification — A4 only removes the client-writable flag; the badge stays server-only until a verification flow exists.
- No password-reset flow (would reduce the blast radius of A3, but is a feature, not a fix).
- No migration from `db push` to `prisma migrate deploy` — B3 only removes the silent-loss flag; adopting migrations is a separate initiative.
- Keeping or deleting the `/workbench` catalog and the wider component kit (see D2 risk).
- Replacing `isomorphic-dompurify` (heavy jsdom dependency) with a lighter tag-stripper — the existing `xss-protection` tests encode DOMPurify's exact output; out of scope.

### A1 — Re-check the session against the database on every request (suspension + session termination become real) — P0
```bash
/ralphy-plan session-db-recheck "A verified JWT is trusted alone for its whole 7-day life, so two security controls the UI already offers are no-ops (repo audit 2026-10-20, findings 1 + 12). Verified roots: lib/session.ts getSession (L60-72) only runs jwtVerify and returns the payload — User.suspended is read ONLY at login (app/actions/auth.ts L96) and the comment at L67 says 'sid-less/row-less tokens still authenticate'; app/actions/settings.ts terminateInactiveSessions (L142-153) and terminateSession (L172-191) delete Session rows that nothing ever reads, so «Завершить все неактивные сеансы» and the per-device terminate leave the other device logged in; Session.lastActiveAt (prisma/schema.prisma L67) has a default and is never updated, so «Активные сессии» (lib/view-models.ts getActiveSessions L1378) shows a device used daily as «7 дн назад» and sorts it last. Test plan: integration — (a) create a session, call terminateSession for it, then getSession with that token → null; (b) suspend a user via suspendUser, then getSession with their valid token → null, and a server action (e.g. createGig) with that token returns the login redirect; (c) a sid-less token for a non-suspended user still validates (existing test); (d) heartbeat advances lastActiveAt and getActiveSessions sorts that session first.
```
