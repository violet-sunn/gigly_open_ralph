# Prod Feedback Fixes — Stress-Test Round 2

**Created:** 2026-07-14
**Status:** PLANNED

## Problem

A second external stress-test pass (report: `Гигли баги.pdf`, 9 defects, all captured on a **phone-width** viewport) surfaced a fresh batch of issues that Round 1 did not touch. They were **verified against the current build** (code inspection + a live Playwright pass on seed data at 390px, 2026-07-14) and break down as: **functional bugs** — accepting an application never starts a chat between client and specialist (#8), and the «Требует внимания» feed never clears after a deal completes (#9); **truthfulness bugs** — a withdrawn application reads as «Отклонён» on the dashboard and the gig detail gives no per-viewer withdrawn/re-apply state (#1, #2); **localization** — the notifications popover and the «Требует внимания» card render in English (#4, #6); and **UX/layout** — the login form wipes both fields on error with an overlapping error plaque (#3), the «Открыть спор» control is a 22px muted text link that doesn't read as a button (#7), and the dashboard/«Мои гиги» renders the desktop layout on mobile with horizontal overflow and no scroll (#5).

## Why This Matters

This is the second outside-user pass before the diploma defense (~2026-07-19) and immediately before wider peer stress-testing — which, on the evidence of this report, will happen **on phones**. A marketplace whose core loop silently fails to open a chat after hire (#8), that mislabels a user's own withdrawn application as rejected (#2), that shows English system notifications (#4/#6), and whose main dashboard is unusable on a phone (#5) reads as unfinished, not «high-end B2B». Round 1 confirmed the pluralization/chip/layout polish; this round closes the remaining functional and mobile-facing gaps so the build is demo-solid on the device reviewers will actually use. Handling it as one coordinated round — functional first, then truthfulness/localization, then UX, then the mobile pass — keeps it shippable instead of a scatter of patches.

## Scope

This initiative fixes defects across the running app; it does **not** re-ground design or change the deploy pipeline. Affected systems (with verified roots):

- **Messaging / acceptance flow** — `app/actions/gig.ts` `acceptApplication` (creates no conversation), the `Message` model + messaging action, `app/(protected)/gigs/[id]/GigDetail.tsx` (no chat affordance at all), `/chats` + dashboard «Сообщения» VM in `lib/view-models.ts` (conversations sourced only from existing `Message` rows). Root of #8.
- **Application status display** — `lib/view-models.ts`: `getSpecialistDashboard` archived-card mapping (~L286-290 collapses `WITHDRAWN`/`WITHDRAWN_FINAL`→`'rejected'`/«Отклонён» though the correct «Отозвано» exists at L508) and `getGigDetail` viewer-application state. Root of #1/#2.
- **Notification feed lifecycle** — `lib/view-models.ts` `getDashboardAttention` (L165: returns 6 most-recent `Notification`s with no read/lifecycle filter), `Notification` model, `app/(protected)/dashboard/DashboardDesign.tsx`. Root of #9.
- **Notification localization** — `lib/notification-utils.ts` `getNotificationDisplayText` (nearly all branches English) + the notifications popover title/relative-time. Root of #4/#6.
- **Auth surface** — `app/_design/AuthDesign.tsx` login form (uncontrolled inputs, no value echo on error; error plaque overlaps the pixel-wave + «Войти»). Root of #3.
- **Dispute CTA** — `app/(protected)/gigs/[id]/GigDetail.tsx` `showDisputeLink` block (L698-714, 13px muted inline `<div>`). Root of #7.
- **Responsive layout (new scope)** — `app/(protected)/dashboard/DashboardDesign.tsx` + the specialist «Мои гиги» layout, `app/_design/AppShellDesign.tsx`, shared layout/tokens CSS. Root of #5.

**Dependencies:** Changes 2 and 3 both edit `lib/view-models.ts` — land them sequentially (or in the same working session) to avoid conflicts. Change 4 (localization) changes the notification *text source* that Change 3 (attention feed) *filters* — independent, but do 4 aware that the attention card title comes from the same function. Changes 1, 5, 6, 7 are independent and may run in any order. Change 7 (mobile) is the largest and is gated on a scope decision (see Risks).

**Process:** Run on a dedicated branch, one commit per change, so a bad fix is easy to revert. After each functional/layout change, verify live in the running app (Playwright flow already used this round — seed login `alexey.ivanov@mail.ru` / `ivan.petrov@techcorp.ru`, `TestPass123`; mobile checks at 390px), not just via tests. Re-deploy to Amvera (`./deploy-to-amvera.sh`) at the end of the round, or per-change if the user wants to re-test incrementally.

**Risks / unknowns:**
- **#5 scope is a genuine product decision.** The app is deliberately desktop-first (Round 1 non-goal), yet every screenshot in this report is a phone. Change 7 must first settle with the user: (A) targeted fix of the reported dashboard/«Мои гиги» at phone widths, vs (B) a general responsive pass. Recommended default: **(A) targeted first**, track (B) separately. Do not silently expand to a full responsive rewrite.
- **#8 fix shape.** «Start a chat on acceptance» can mean (i) seed an initial system/greeting `Message` so the thread materializes for both parties, and/or (ii) add a «Написать» affordance that opens the (possibly empty) gig-scoped thread. Confirm which with the user; the safe baseline is both (a persisted opener + an entry point) so the thread is discoverable from `/chats`, the dashboard «Сообщения» panel, and the gig detail.
- **#1 is partly done.** The withdrawal *mechanic* already works (re-apply form returns after a reversible withdrawal — verified live). What remains is truthful *display* (per-viewer «Вы отозвали» state vs the gig's derived «На рассмотрении»). Scope Change 2 as display-layer only; do not re-touch the lifecycle state machine.
- **#9 read-state.** Filtering «Требует внимания» by "unread" needs a reliable read signal (`Notification.lastReadAt` / a read flag). Confirm the field exists (or add it) as part of Change 3; the terminal-gig-status filter (COMPLETED/PAID) works regardless and is the minimum.

## Non-goals / Deferred

- No design re-grounding, no new UI kit, no deploy/infra changes.
- **General responsive rewrite** across all screens is **out of scope** unless the user chooses option (B) in Change 7; the default deliverable is the reported dashboard/«Мои гиги» only.
- No change to the fixed-price application/terms state machine (Round 1 owns it); Change 2 is display-only.
- Notification delivery channels (email/push) are unchanged — this round localizes existing in-app text only.

Each is a separate `/ralphy-plan` → `/ralphy-implement` cycle. Ordered by priority: functional bugs (1–3), then localization/truthfulness display (already partly in 2), then auth/UX (4–6), then the mobile pass (7). Changes 2→3 share `lib/view-models.ts` (sequence them); the rest are independent.

### 1. Start the chat on application acceptance (#8)
```bash
/ralphy-plan chat-on-acceptance "After a client accepts a specialist's application, no chat is created between them and there is no way to start one — reported «Не запускает чат с Заказчик и Исполнитель после принятия заявки» (Гигли баги #8). Verified against the build: acceptApplication (app/actions/gig.ts:531) only flips application/gig statuses and fires an application_accepted notification — it never creates a Message or conversation; app/(protected)/gigs/[id]/GigDetail.tsx has NO chat affordance (grep finds no «Написать»/«Открыть чат»); /chats and the dashboard «Сообщения» panel list conversations sourced purely from existing gig-scoped Message rows, so an assigned gig with zero messages shows no thread for either party. Requirements: (1) on acceptApplication, initiate the gig-scoped conversation between the client and the assigned specialist so a thread exists immediately for BOTH — e.g. persist an initial system/greeting Message on the gig (decide with the user: system opener vs an empty-but-listed thread; baseline = a persisted opener so it appears in /chats and the dashboard «Сообщения» for both); (2) add an obvious «Написать заказчику»/«Написать исполнителю» control on the gig detail (GigDetail.tsx) for the assigned specialist and the owning client while the gig is IN_PROGRESS/REVIEW, routing into that gig's chat; (3) ensure the new conversation surfaces in the dashboard «Сообщения» VM too. Files: app/actions/gig.ts (acceptApplication), Message model + messaging/sendMessage action, app/(protected)/gigs/[id]/GigDetail.tsx, lib/view-models.ts (getSpecialistDashboard/getClientDashboard messages + /chats conversation list). Test plan: E2E — client accepts a pending application → both client and specialist immediately see a chat thread for that gig in /chats and can send a message; the gig detail exposes a working «Написать» entry point for both roles. Verify live."
```

Test plan: E2E — apply then withdraw → dashboard card reads «Отозвано» (not «Отклонён»); gig detail shows «Вы отозвали» + a working re-apply rather than a bare «На рассмотрении»; re-apply → returns to «На рассмотрении». ### 3. Clear «Требует внимания» after a deal resolves (#9)
```bash
/ralphy-plan attention-feed-lifecycle "The «Требует внимания» dashboard block never clears — after a deal is completed it still shows a card (e.g. «Your application was accepted» → «Открыть») for a gig already marked Завершён/COMPLETED (Гигли баги #9). Verified: getDashboardAttention (lib/view-models.ts:165) returns the user's 6 most-recent Notification rows unconditionally — no filter by read state, by age, or by the linked gig's lifecycle — so an acceptance notification lingers forever. Files: lib/view-models.ts getDashboardAttention, Notification model (read-state field if missing), app/(protected)/dashboard/DashboardDesign.tsx (empty-state handling when the feed becomes empty). Test plan: E2E — complete a gig that produced an acceptance notification → «Требует внимания» no longer lists it and its count drops; a still-actionable unresolved notification remains. Verify live."
```
