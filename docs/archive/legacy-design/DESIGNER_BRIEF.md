# Что нужно от дизайна в Figma для передачи в разработку

**Версия:** 1.0 · Платформа Gigly · **Только десктоп**

---

## Контекст (важно прочитать)

Мы собираем экраны в код частично автоматически — через **Figma Dev Mode**. Чтобы это
работало точно, а не «примерно похоже», Figma-файл должен быть **собран по правилам**
(на переменных, стилях и компонентах), а не просто нарисован «картинкой».

Чем строже собран файл, тем точнее и быстрее получится результат в коде.

Делаем **только десктоп**. Мобильную/планшетную версию не проектируем.

### Выводы и решения

1. **Фундамент хороший** (variables/styles + компоненты + auto layout + шрифты) — можно опираться.
2. **Пока дизайн в черновике** — делаем только подготовку, не зависящую от финала:
   обновить токены, выгрузить PNG ключевых экранов, собрать карту компонентов из кода.
   Реальную сборку экранов в код начинаем после фиксации макета.
3. **Dev Mode пока не продлеваем** — он нужен на этапе реальной сборки (точечное
   извлечение значений + Code Connect). Без него уже сейчас доступны: выгрузка токенов
   плагином Design Tokens, экспорт PNG, список компонентов. Продлеваем, когда дизайн
   финализирован и стартует сборка в код.

> Это не «претензии» — по ответам мы понимаем, что уже готово, а что нужно доделать.

## 1. Качество и охват экранов

- [ ] **Финальная детализация** (high-fidelity), а не наброски/вайрфреймы.
- [ ] **Базовая ширина десктопа** зафиксирована (обычно **1440px**) — указать какую. Мобильную версию **не делаем**.
- [ ] Каждый экран — **отдельный именованный Frame**, сгруппированы по разделам/флоу.
- [ ] **Все нужные экраны**, а не только несколько ключевых (нужен полный список — см. п.6).
- [ ] Для каждого экрана показаны **все состояния**, а не только «когда всё хорошо»:
  - [ ] заполненное (с данными);
  - [ ] **пустое** (нет гигов / нет заявок / нет уведомлений);
  - [ ] **ошибка и валидация** форм (как выглядит поле с ошибкой);
  - [ ] загрузка (если предполагается);
  - [ ] различия по ролям, где интерфейс отличается (**Клиент / Специалист / Админ**).
- [ ] Для кнопок/полей/ссылок показаны состояния **hover / focus / active / disabled**.

---

## 2. Дизайн-система: переменные, стили, токены

- [ ] **Все цвета** — через Variables/Styles с понятными смысловыми именами
      (например `surface/level-0`, `text/strong`, `brand/default`), а не «Blue 500».
- [ ] **Вся типографика** — через Text Styles (заголовки, текст, подписи), с именами.
- [ ] **Отступы и размеры** — по единой шкале (желательно тоже переменными).
- [ ] **Тени, скругления** — через Styles/Variables.
- [ ] Нигде нет «случайных» hex/пикселей мимо переменных.
- [ ] ⚠️ **Заново выгрузить токены** плагином **«Design Tokens» (Lukas Oppermann)** —
      тем же, что использовался раньше, — и прислать обновлённый JSON.
      *(Текущий файл токенов устарел — это нужно сделать в первую очередь.)*

---

## 3. Компоненты («детали конструктора», которые мне нужны от тебя)

- [ ] Повторяющиеся элементы собраны как **Figma Components**, а не копипастом:
  - кнопки, поля ввода, выпадающие списки, чекбоксы/радио;
  - карточки (гига, специалиста, заявки);
  - бейджи/статусы, теги;
  - модальные окна и диалоги подтверждения;
  - тултипы, уведомления, пагинация;
  - навигация / шапка / меню;
  - «пустые состояния».
- [ ] Разные виды и состояния — через **Variants**
      (например, Button: `variant=primary/secondary/ghost`, `state=default/hover/disabled`).
- [ ] Компоненты на **Auto Layout**.
- [ ] **Стабильные, осмысленные имена** компонентов (их нельзя потом хаотично переименовывать).
- [ ] Отдельная страница-**библиотека** со всеми компонентами, чтобы был виден полный список.

---

## 4. Иконки, ассеты, шрифты

- [ ] Иконки — как компоненты, **экспортируемые в SVG**; указать, какой набор иконок используется.
- [ ] Логотип, иллюстрации, изображения — в экспортируемом виде.
- [ ] **Шрифты:** перечислить семейства и начертания **и приложить файлы или ссылку на
      источник/лицензию** (без файлов мы не сможем их подключить).

---

## 5. Dev Mode и аннотации (легко, прямо в Figma)

- [ ] Дать доступ к файлу в **Dev Mode**.
- [ ] На ключевых экранах добавить короткие **аннотации**: что кликабельно, куда ведёт, что делает кнопка.
- [ ] Где элемент = готовый компонент, это должно быть видно (использован Component,
      а не нарисовано заново) — это позволит связать Figma с кодом (**Code Connect**).

---

## 6. Документы (минимум, без тех. деталей — это не твоя задача)

Подробные спецификации экранов **пишет разработка**, ты их только проверяешь.
От тебя нужны только лёгкие вещи:

- [ ] **Список экранов** в работе с одной строкой назначения каждого
      («Дашборд клиента — обзор его гигов и заявок»).
- [ ] **Схема переходов** (даже простая, со стрелками): из какого экрана куда попадаешь.
- [ ] **Список компонентов** с их названиями.
- [ ] Короткие заметки по нестандартному поведению (можно прямо аннотациями в Dev Mode).

---

## 7. Доступ и передача

- [ ] Ссылка на Figma-файл с доступом (Edit или Dev Mode).
- [ ] Обновлённый **JSON токенов** (из п.2).
- [ ] Договорились о **правилах именования** переменных/компонентов и больше их не ломаем.

---

## Минимум для старта vs полный набор

**Минимум, чтобы начать прямо сейчас:**
- свежий JSON токенов;
- 2–3 ключевых экрана в финальном качестве, собранные на переменных/компонентах;
- список всех планируемых экранов;
- доступ к Dev Mode.

**Полный набор (чтобы пройти весь редизайн без затыков):**
- всё из чеклистов выше: все экраны, все состояния, полная библиотека компонентов,
  иконки/шрифты, аннотации.

---

## Как мы будем работать дальше (для понимания)

1. Ты обновляешь токены и собираешь экраны по правилам выше.
2. Разработка делает **карту соответствия** «компонент Figma → компонент в коде».
3. По каждому экрану разработка пишет **черновик описания**, ты его **проверяешь и правишь**.
4. Экран собирается в код (**новый внешний вид, существующая логика/бэкенд**), затем
   автоматически сравнивается скриншотом с твоим макетом и доводится до совпадения.
