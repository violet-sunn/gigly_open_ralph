# Деплой Gigly на Amvera Cloud

Проверено локально: собранный образ поднимается, применяет схему, засеивает демо-данные
(35 пользователей, 53 гига, 192 отклика), логин/редиректы работают, при перезапуске данные
сохраняются и сид не повторяется.

БД — обычный SQLite-файл на постоянном диске Amvera (`/data/prod.db`). Никакой Turso/внешней БД.

## Что уже лежит в репозитории

| Файл | Роль |
|------|------|
| `Dockerfile` | сборка прод-образа (node:20, `next build`, всё в одном образе) |
| `docker-entrypoint.sh` | на старте: `prisma db push` → сид один раз → `next start` |
| `amvera.yml` | `containerPort: 3000`, `persistenceMount: /data` |
| `.dockerignore` | не тащит в образ dev.db, секреты, тесты |
| `.env.production.example` | список переменных окружения для Amvera |

## Шаги (≈15 минут)

1. **Регистрация.** Создай аккаунт на https://amvera.ru (вход по РФ-почте/телефону, оплата РФ-картой).

2. **Создать проект.** В панели: `Создать проект` → тип `Приложение`. Способ доставки кода — Git
   (Amvera даст свой remote, например `https://git.amvera.ru/<user>/<project>`). Amvera сам увидит
   `Dockerfile` и `amvera.yml` в корне пуша.

3. **Переменные окружения.** Проект → `Настройки` → `Переменные окружения`. Добавь:
   - `SESSION_SECRET` — **отметь как секрет.** Сгенерируй длинную случайную строку.
     В этой сессии можешь выполнить: `! openssl rand -base64 48`
   - `DATABASE_URL` = `file:/data/prod.db`
   `NODE_ENV=production` уже зашит в образ — отдельно задавать не нужно.

4. **Задеплоить — только приложение, без ноу-хау.** Пушим НЕ весь репозиторий (там openspec/,
   gigly_full_design/, design-reference/ и т.д. — твой рабочий метод, он не должен уходить на сторону),
   а только файлы приложения. Для этого есть скрипт `deploy-to-amvera.sh`:
   ```
   ! git remote add amvera <URL-из-панели-Amvera>
   ! ./deploy-to-amvera.sh
   ```
   Скрипт собирает снапшот только из нужного (`app/ lib/ prisma/ public/ scripts/` + конфиги +
   Dockerfile/amvera.yml), вырезает локальную БД и мусор, и force-пушит его в `amvera:master`.
   На git-сервер Amvera попадает **только приложение** (проверено: 345 файлов, ни specs, ни dev.db).
   Первая сборка идёт несколько минут.

5. **Проверить.** Открой выданный Amvera URL (`https://<project>-<user>.amvera.io`). Должен открыться
   русский лендинг. Тестовый вход: `admin@gigly.ru` / `TestPass123` (или `alexey.ivanov@mail.ru`,
   `ivan.petrov@techcorp.ru` и т.д. — пароль у всех демо-аккаунтов `TestPass123`).

## Тариф

Хватает минимального с ≥1 ГБ RAM (Next.js `next start` укладывается). Диск — небольшой том
для `/data` (SQLite-файл + аплоады весят мегабайты).

## Обновления и обслуживание

- **Выкатить изменения:** снова `./deploy-to-amvera.sh` — соберёт свежий снапшот приложения и
  запушит. Amvera пересоберёт и перезапустит, данные в `/data` сохранятся, повторного сида не будет.
  (Скрипт снимает снапшот с текущего рабочего каталога, так что коммитить перед деплоем не обязательно.)
- **Логи/перезапуск:** в панели Amvera (вкладки «Логи», кнопка перезапуска).

## Данные: что сидится в проде

По умолчанию прод засеивается **минимально** — `prisma/seed.prod.ts`: 5 категорий, один помеченный
демо-владелец `demo@gigly.ru` (Gigly · Демонстрация), 5 примеров-гигов (`isExample`, на них ведут
ссылки из создания гига) и админ `admin@gigly.ru`. Никаких фейковых компаний/специалистов/массы гигов.

- **Полный демо-набор** (34 юзера, 53 гига и т.д. из `prisma/seed.ts`) — только для разработки.
  Если он зачем-то нужен на сервере: переменная **`SEED_DEMO=true`** (этап запуск).
- **Пароль админа:** по умолчанию общий демо-пароль `TestPass123` — для публичного прода это слабо.
  Задай переменную **`ADMIN_PASSWORD`** (этап запуск), и админ создастся с ней (хешируется на старте).
  Меняет пароль только при чистом засеве (см. `RESET_DB` ниже).
- **Пересеять базу начисто:** переменная **`RESET_DB=true`** (этап запуск) → при следующем старте
  контейнер сотрёт `/data/prod.db` и пересеет. Срабатывает **один раз** (защита от случайного стирания
  реальных данных: ставится маркер `/data/.reset-applied`). Чтобы сбросить ещё раз позже — удали этот
  маркер или пересоздай том. После первого чистого засева `RESET_DB` можно убрать.

## Важные детали (почему сделано так)

- **`prisma db push`, а не `migrate deploy`:** источник истины — `prisma/schema.prisma`; миграции
  отстают от него (поздние поля вроде `currency`/`notifyNewGigs`). `db push` синхронизирует БД со
  схемой ровно как в dev/E2E, так что колонок не будет не хватать.
- **`SESSION_SECRET` обязателен:** контейнер не стартует без него (fail-fast) — чтобы прод не
  поднялся на слабом дефолтном ключе.
- **`secure`-куки:** при `NODE_ENV=production` сессионная кука `secure`. Amvera отдаёт HTTPS —
  всё работает. (Не открывай приложение по «голому» http — куки не пойдут.)
